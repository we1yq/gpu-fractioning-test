# 实验设计：显存硬限制对 MPS 干扰的影响

## 研究问题

显存硬限制会影响两类争用：

| 类型 | 资源 | 硬限制是否直接参与 |
|---|---|---|
| **运行时争用** | SM、L2、显存带宽、PCIe | 否，未触及上限时不参与 |
| **容量争用** | 显存能否放下 | 是，这是硬限制要解决的问题 |

1. **Q1**：运行时争用在什么条件下出现？硬限制会让它减轻、不变还是加剧？
2. **Q2**：总需求超过显存时，硬限制提供多少保护？
3. **Q3**：硬限制自身带来多少分配开销？驱逐会不会影响邻居？
4. **Q4**：相比传统 MPS，Fractioning 这套配置有多少开销？

## 假设

| 编号 | 假设 | 依据 |
|---|---|---|
| H1 | 运行时争用基本不变 | 限制只在分配和释放时检查，不隔离 L2 和带宽 |
| H2 | 分配开销增加不大 | `misc` 后端每次分配只是查表、比较、扣减 |
| H3 | 容量争用明显减轻 | 每个客户端被限制在配额内 |
| H4 | 驱逐可能影响邻居 | 官方文档没有保证，MPS 客户端共享故障域 |

这些都是实验前的预测，不是结论。

## 实验组

| 组 | 环境 | request | limit | 作用 |
|---|---|---|---|---|
| **A** | KAI + Fractioning `sm-sharing` | 10 GiB | 40 GiB | 硬限制形同虚设，主线对照 |
| **B** | KAI + Fractioning `sm-sharing` | 10 GiB | 10 GiB | 硬限制真正起作用 |
| **C** | KAI `NonMemoryEnforced` + 节点上的传统 MPS | `gpu-fraction` 0.25 | 无 | 硬限制出现之前的真实做法 |

| 比较 | 回答 |
|---|---|
| A 和 B | 硬限制起作用时有什么影响（Q1、Q2、Q3） |
| A 和 C | 新版 MPS 这套配置的开销 |
| B 和 C | 相比传统 MPS 的总差异（Q4） |

### 为什么这样选

- A、B 的 Pod、调度器、MPS server、`memacct`、`context-share` 全部相同，只差一个注解值。
- A、B 可以逐组交替运行，时间漂移不会集中到某一组。
- 10 GiB 是 n=4 时的公平份额（40 GiB / 4）。运行时负载碰不到这个上限，所以运行时结果不依赖
  这个数值。容量实验中它决定谁能拿到多少显存。
- C 组是 KAI 文档中的官方 MPS 用法，Pod 结构和 A、B 相同。
- 不用 device plugin 的 `sharing.mps`：官方 README 说明它把显存和算力都限制为 1/N。

### 控制变量

所有组相同：显卡型号、负载及大小、并发数、随机种子、CPU 配额和线程数、NUMA 节点、
PyTorch 镜像、不设 SM 上限。

### 已知局限

| 局限 | 处理方式 |
|---|---|
| A 组仍有 `memacct` 记账，也有 10 GiB 软限制 | 这部分差异由 C 组回答 |
| C 组和 A、B 不能交替运行 | C 组单独一批，前后各跑一组 A 校验漂移 |
| Pod 可能落在任一张卡上 | 记录 UUID，先比较两张卡的差异 |
| `gemm`、`membw` 会撞 250 W 功耗上限 | 记录时钟和降频原因，时钟差异过大的组单独标记 |
| 内核 5.15 只有 `misc` 后端 | 结论只代表 `misc`。官方未提供两种后端的性能对比 |
| 开环低负载时 GPU 降频 | 受害者只在相同条件的组之间比较 |

## 阶段 0：前置验证

| 检查 | 通过标准 |
|---|---|
| `sm-sharing` 下超配额是否触发 OOM | OOM，退出码 2 |
| A、B 在 n=4 时能否调度 | 4 个 Pod 全部运行，否则 request 改用 9 GiB |
| 两张 A100 的差异和运行噪声 | 确认判定阈值 |
| C 组能否跑通 | Pod 连上节点 MPS，并确认没有显存和 SM 上限 |

## 阶段 1：运行时争用（Q1，约 13 组）

每个来源只选代表性负载，用来确认是否有差异。出现意外差异时再扩展。

| 条件 | 组合 |
|---|---|
| SM 饱和 | `gemm` n=1、2、4 |
| 长短 kernel 混合 | `smallkernel@100` n=1；配 `gemm` 4096；配 `gemm` 8192 |
| 显存带宽 | `membw` n=1、2 |
| PCIe | `hostcopy` n=1、2；`gemm` 配 `hostcopy` |
| L2 | `membw` 每数组 13 MiB，n=1、2（合计工作集约 78 MiB，超过规格约 40 MiB 的 L2） |

## 阶段 2：容量争用（Q2，新主线）

Pod 错开启动，先到的先占显存。每个 Pod 先申请显存，再运行 `gemm` 2048 作为活动探针。

| 场景 | 设计 | 观察指标 |
|---|---|---|
| `cap-fair` | 4 个 Pod 各想要 15 GiB，总需求 60 GiB | 每个 Pod 实际拿到多少、谁失败、探针延迟 |
| `cap-hog` | 贪婪 Pod 要 38 GiB，受害者要 2 GiB，旁观者要 1 GiB | 受害者能否运行、贪婪 Pod 是否被驱逐、旁观者是否受影响 |

预期差异：B 组贪婪 Pod 被限制在 10 GiB。A 组它能占满，后到者可能触发驱逐。C 组没有驱逐，
后到者可能直接失败。

## 阶段 3：分配开销和驱逐（Q3，4 组）

新负载 `alloccycle`：循环申请、写入、释放，每次调用 `empty_cache()` 把显存还给驱动。

| 组合 | 测什么 |
|---|---|
| 64 MiB，n=1 | 单次分配基线 |
| 1 GiB，n=1 | 分配大小的影响 |
| 64 MiB，n=2 | 多客户端同时分配 |
| 64 MiB，n=1，预先占用 9216 MiB | 接近配额时的分配 |

驱逐是否影响邻居由 `cap-hog` 的旁观者观察。

## 判定标准

实验前固定，避免看到数据后再调整：

- 运行时和分配开销：每组至少 5 轮，报告均值和比值的 95% 置信区间。
  - **不变**：区间完全落在 0.97～1.03 内。
  - **加剧**：区间整体高于 1.03。**减轻**：区间整体低于 0.97。
  - 其他情况判为**不确定**，需要增加轮次，不能算作“不变”。
  - 3% 这个阈值要根据阶段 0 测到的噪声确认。
- 容量争用：报告每轮的实际结果（获得的显存、失败、驱逐），不做均值替代。
- 被剔除或过载的轮次要单独报告，不能静默丢弃。

## 运行时长估算

19 组 × A、B 两组，每次约 70 秒，每轮约 45 分钟，5 轮约 3.7 小时。C 组每轮约 22 分钟。

## 显存限制的实现路径

依据 `kai-scheduler/gpu-fractioning` v0.1.8、`nvidia-container-toolkit`、
`open-gpu-kernel-modules` 615.71.10 的源码和服务器实测：

1. KAI 选定 GPU，按 `request` 调度，写入容器级注解。
2. `fractiond`（NRI 插件）在容器创建时注入 `NVIDIA_GPU_MEMORY_REQUEST`、
   `NVIDIA_GPU_MEMORY_LIMIT`、`NVIDIA_VISIBLE_DEVICES`，并挂载 MPS 管道。
3. NVIDIA 工具包的 CDI 钩子 `apply-cuda-memory-limits` 读取这些变量，定位容器的 cgroup，
   调用 NVML 的 `SetMemoryLimits_v1` 设置软、硬限制。
4. 负载通过 `mpsd` 管理的 MPS（v3、`memacct` 开启）运行。`sm-sharing` 连接共享服务器
   （`context-share`），`time-slicing` 连接默认 socket。
5. 内核没有 `dmem` 时，驱动使用 fallback：把 cgroup 当作查找键，在自己的表里保存限制和
   剩余额度，每次分配时比较并扣减。这解释了容器的 `misc.max` 为空。

实测：`request` 2 GiB、`limit` 4 GiB 时，软限制 2048 MiB，硬限制 4096 MiB，只作用于分配到的 GPU。
`request` 10 GiB、`limit` 40 GiB 时，软限制 10240 MiB，硬限制 40960 MiB。

## 未确认事项

- `misc` 后端的软限制驱逐是否真能工作。`cap-hog` 会验证。
- C 组在 Pod 内能否连接节点 MPS，官方示例只挂载了管道目录。
- 官方没有说明请求方自身超过软限制时的处理。
- L2 约 40 MB 来自第三方规格列表，未经官方确认。
